# CLAUDE.md

Rules for coding agents in this repo. Setup, env vars and deployment are in README.md.

- Never replace `ENCRYPTION_KEY` without setting `ENCRYPTION_KEY_PREVIOUS` to the old value in the same deploy, and remove `ENCRYPTION_KEY_PREVIOUS` only after the key sweep logs `[key-sweep] SAFE` (README, "Rotating `ENCRYPTION_KEY`").
- Turn a wall time into an instant only with `wallTimeToInstant` (`src/utils/wall-time.ts`, re-exported by `calendar-write/walltime.ts`): a time the clocks skip moves forward by the jump, a repeated one is its first occurrence, whatever zone the server runs in. Never `fromZonedTime`, and never move a `Date` by its local fields (`setHours`, `setDate`, `setSeconds`, ...): both depend on the server's zone, so use epoch arithmetic (`new Date(Date.now() - 24 * 60 * 60 * 1000)`) or the resolver. Read a zone's clock for logic with `instantToWallTime` (`src/utils/wall-time.ts`); `formatInTimeZone` is display-only, because it reads an hour late in the server's own skipped hour. `scripts/smoke-dst.ts` fails on the first two (it re-runs itself under three process zones). Never read a `Date` made from a wall-time or date string through the server's zone either (`new Date('yyyy-MM-ddTHH:mm').getHours()`, `new Date(x.toLocaleString('en-US', { timeZone }))`, a plain date's weekday without `timeZone: 'UTC'`): take the hour from the text (`.slice(11, 13)`), a plain date as the UTC day it names, a zone's day from `instantToWallTime` (the Hebrew date of one is `hebrewDateAt`, `src/services/hebrew-date-resolve.ts`); the same smoke scans `src/`, `app/` and `components/` for it.
- A send to a person that no one asked for (a cron pass, a nudge, a notice) asks `isPaused(user, at, '<kind>')` (`src/services/zmanim/pause.ts`, the Shabbat and Yom Tov pause) before it sends (the third argument names the send, and a paused one logs `[pause] skipped <kind> for <userId>`). Replies to the person's own actions and messages to the admin do not: web sign-up's sends are such replies (the sign-up code, `sendNoticeEmail`'s notice that a sign-in way was added, and the bot's Connect Telegram replies in `src/services/telegram-connect.ts`). A send skipped because the person has no chat (an account made on famcal.bot has no Telegram and no WhatsApp) logs one line, `[<send>] skipped user <id>: no Telegram` for a Telegram-only send or `[google-sync] user <id>: no chat; no reconnect message` for the Google reconnect message, and is never marked sent (the one exception is a native reminder's occurrence: the pass claims it without a send and logs `[native reminder ping] skipped user <id>: no chat and no device`, so a device turned on later does not fire an old one). `scripts/smoke-pause.ts` lists every file that sends and fails on one nobody classified, so a new sender is added to its `PAUSED` or `NOT_PAUSED` table with the reason.
- A reminder by zman (`NativeEvent.zmanSpec`, date-only) is due at its zman at each recipient's own place. Every reader gets a reminder's due time from `dueAtForOccurrence` / `reminderDueAt` (`src/services/native-reminders/due.ts`) given the person's `ZmanClock` (`zmanClockFor` in `src/services/zmanim/reminder-clock.ts`, which asks `zmanInstant` and nothing else): the pass, the home, the digests and the summaries. Never store the computed time in `startsAt`, never count a zman anywhere else, and never import `src/services/zmanim` into a `'use client'` file: the Mini App gets the times in the DTO, in the editor info and in the sun sheet's list (`GET /api/zmanim`, `zmanDayList` in `src/services/zmanim/reminder-times.ts`, the person's wrapper over `zmanDayForPlace` in `src/services/zmanim/day-list.ts`). The list shares the editor info's rows (`zmanRows`), and its window rows come from `restDayBlocks` (`compute.ts`: every Shabbat and Yom Tov block, its start or end null where the sun makes none); the pause reads `shabbatYomTovWindows`, which is the complete blocks. The ends are the blocks' ends, the candle lighting is always the day's own `instantAt` (20 minutes before the plain sunset row), also on an eve whose block has no end (its end row is a dash), and the pause starts at the eve's sunset, so the list and the pause never disagree (a Friday or a rest day inside a longer block takes its own day's time from the same `instantAt`). The public zmanim pages (`app/[locale]/(site)/zmanim`) call the same `zmanDayForPlace` with a memo of their own per page and `quiet: true`, never the process memo, and a city's zone is its Israel flag (`inIsrael`; every Israeli city is `Asia/Jerusalem`): it decides the Yom Tov days, the height, the Sephardi end of Shabbat and the holidays' `{ il }`.
- The 5-minute event alerts pass reads the FamCal store only while the event alerts gate is open (`src/services/event-alerts-gate.ts`): Neon suspends after 5 idle minutes and bills every awake one, so an idle pass makes no database query. A write that can add a FamCal alert or move one earlier opens the gate after its commit (`openEventAlertsGate()`); the event store's four writes (`createNativeEvent`, `createNativeSeries`, `updateNativeEvent`, `deleteNativeEvent`) do, so FamCal events are written only through them. `scripts/smoke-alerts-gate-writers.ts` lists every file that writes FamCal events, calendars or pairings and fails on one nobody classified, so a new writer goes in its `OPENS` or `NO_NEW_ALERT` table with the reason. The three gates (this one, the native reminders' due gate, the copy to Google) are one mechanism, `src/utils/pass-gate.ts`, on `globalThis`, with the ceiling at the next whole UTC hour.
- Every call to Google retries through the one policy in `src/services/google-retry.ts`: `GOOGLE_RETRY_CONFIG` on the OAuth2 client's transporter (`getGoogleAuth`, the only factory) and `googleFetch` for a raw fetch (`{ wholeJson: true }` for a GET whose JSON is read: the body is read in the attempt, so one that comes cut off is retried like no answer). Never add a retry loop, a fixed sleep or `retry: n` of your own around a Google call (the calendar reader's per-call `retry: 1` is the one override). It retries 408, 429, 5xx, no answer and a 403 `rateLimitExceeded`/`userRateLimitExceeded`; `quotaExceeded`/`dailyLimitExceeded` are left to the caller; a POST to the Calendar API only on a rate limit. It waits max(`Retry-After`, jitter) and rethrows at once when `Retry-After` is over 10 s, so a durable layer (the copy worker's per-user cooldown) decides. Classify a failure only with `classifyGoogleError`, never by `code === 403` or the message (a 403 is usually a rate limit or a refusal, not a dead token); `retryAfterMs`, `googleRateLimitKind` and `isGoogleRateLimit` live in `calendar-read/google-map.ts`. `scripts/smoke-google-retry.ts` pins it. A browser notification sent through Google's push service (FCM, `fcm.googleapis.com`) is no Google API call: it goes through `fetchWithRetry` like every push service (the rule below).
- Every call to a third party other than Google's APIs (MET Norway's forecast, the dust files on S3, every browser push service, FCM included: `sendWebPush`, src/services/web-push/send.ts, and WhatsApp's Cloud API: src/services/messaging/whatsapp-adapter.ts, whose refusals, every 4xx but 429, come back as answers through `okStatuses` so Graph's error is read, and Telegram's guest answer: `answerGuestQuery`, src/services/messaging/telegram-adapter.ts, with `telegramRetryVerdict`) retries through the one loop in `src/utils/fetch-retry.ts`: `fetchWithRetry` for a fetch, `fetchAndReadWithRetry` for a GET whose body is read (the read is in the attempt, so a body that comes cut off or does not parse is retried like no answer: MET's forecast and Telegram's sign-in documents, through `wholeJson`, `src/utils/whole-json.ts`), `retryWithBackoff` for any other async step (the dust reader). Never add a retry loop, a fixed sleep, an attempt counter or a timeout of your own around such a call (it runs to the provider's ceiling). It retries 429, 5xx and no answer up to 3 times after max(`Retry-After`, a full-jitter backoff from 500 ms); any other status (`HttpStatusError`) and a `Retry-After` over 10 s fail at once; the caller logs the give-up in `onGiveUp`. Google's APIs are not here: their policy is the rule above. `scripts/smoke-fetch-retry.ts` pins it, and `scripts/smoke-whatsapp-retry.ts` the adapter.
- Every Bot API call goes through the one `Api` that `getBot()` builds (`src/services/telegram/bot.ts`, node-telegram-bot-api 2.x) with `TELEGRAM_API_OPTIONS` (`{ maxRetries: 0, timeoutMs: 0 }`: the library's own retries would send a message twice when an answer is lost); a failure is read only through `telegramErrorInfo` (`src/lib/telegram-errors.ts`; a refusal's words, such as an edit's "message is not modified", through `telegramRefusalSays`), never by an error's class, `.response` or message (the one exception is `isUnreachableError`'s fallback in `src/lib/delivery-errors.ts`, for an error that reaches it as text only). `scripts/smoke-telegram-wire.ts` (which also builds the client through `getBot()` itself) and `scripts/smoke-telegram-errors.ts` pin both.
- The database client is built only by `createPrismaClient` (`src/utils/prisma-client.ts`; Prisma 7 with the `prisma-client-js` generator and `@prisma/adapter-pg` on the pooled `DATABASE_URL`; migrations read `DIRECT_URL` through `prisma.config.ts`, and Prisma loads no `.env`). Its pool is `PRISMA_POOL` (`max` 5, idle 60 s) with no connect timeout of our own, and a pool failure is reported by `reportPoolError`, by its kind only (a pg message can name the host). A raw query (`$queryRaw`, `$executeRaw`, never `…Unsafe`) gives every parameter a type from its column or a cast (`${x}::int`, `${at}::timestamptz`): the adapter sends parameters untyped, so a bare `${x}` fails (42P18) or comes back as text; a new one goes in `RAW_SQL` of `scripts/smoke-prisma-client.ts` with how its parameters get their types. A database that could not be reached and a transaction that could not start are retried only by `withRetry` (`src/utils/db-retry.ts`: P1001, P2010 with `DatabaseNotReachable`, P2028 "Unable to start a transaction", a connect's `AggregateError`), never anything that may have run. `prisma`, `@prisma/client` and `@prisma/adapter-pg` move together and pinned; never `prisma@latest` (it can be a release candidate). `scripts/smoke-prisma-client.ts` pins all of it.
- The app reads no Open-Meteo API (its free API forbids commercial use; `scripts/smoke-no-open-meteo.ts` fails on one of its API hosts, `…api.open-meteo.com`, in the app's code (`src/`, `app/`, `components/`, `i18n/`, `proxy.ts`); its open data on S3 and the credit link are allowed). A forecast comes only from `fetchWeather(location, timezone)` (`src/services/weather/forecast.ts`, MET Norway's Locationforecast `complete`) with the place's own zone, never a default one (the calendar home header's forecast is the same call, from `GET /api/home-weather` through `homeWeatherOf`, `src/services/weather/home-weather.ts`; its answer carries the person's own place text and the next four days for their own screen, never coordinates, and never a log): its User-Agent `FamCal/1.0 (+https://famcal.bot)`, coordinates at 2 decimals, no request before the stored answer's `Expires` and `If-Modified-Since` after it (one Redis key per rounded place), and one mapper (`mapMetForecast`) for units, the place's days and MET's symbols. A day's rain is its millimetres and hours (`RainSpell`), worded only by `src/services/weather/rain.ts`. Dust comes only from `fetchAirQuality` (CAMS from Open-Meteo's open data on S3, the API's `auto` domains, `@openmeteo/file-reader` pinned and server only). A place's zone comes only from `zoneForCoords` (`src/lib/zone-for-coords.ts`, re-exported by `src/lib/timezone.ts`: geo-tz's default 1970 map, Asia/Jerusalem where it is among the answers, the open sea and a failed lookup null and logged, never defaulted), and its height in Israel only from the stored map (`highestHeight`, `src/services/zmanim/heights.ts`). None of them reaches a `'use client'` file, and the credits the licences ask for stay on the /weather photo and reply (`bot.weatherCredit`, Open-Meteo.com linked in the reply) and in the site footer (`site.footer.dataSources` with `src/site/data-sources.ts`; the zmanim pages' height notice is `src/site/zmanim/sources.ts`), and in no summary (owner's decision); the repo's own data files carry theirs in `NOTICE`. No console line, Sentry message or tag holds a place's name or coordinates (Sentry attaches console lines to later error reports): log the user id, the zone, a cached or fresh flag or the status (`scripts/smoke-no-open-meteo.ts` scans for it).
- The bot turns what the model said about a zman into a reminder's rule only through `readZmanFromModel` (`src/services/zmanim/spec.ts`), and times it only through `zmanClockFor`. A zman name with several opinions in the person's set and none said is never defaulted: the card offers one button per opinion. Every card and reply line for a reminder by zman gets its words and time from `reminderZman` (`src/services/native-reminders/zman-view.ts`) and nothing else, and such a reminder is never created without its card.
- The Jewish times API (`/api/v1/*`; spec `docs/superpowers/specs/2026-11-07-zmanim-api-design.md`, reference `docs/api/jewish-times-v1.md`) answers only from `zmanDayForPlace` (the request's own memo, `quiet: true`) and `restBlocksBetween` (`src/services/zmanim/rest-blocks-view.ts`, which the city pages' "ahead" section calls too), shaped by `src/services/zmanim/api-view.ts`, and every request goes through `handleApiV1` (`src/lib/api-v1/handle.ts`). A key is read only through `findApiKey` (`src/services/api-keys/lookup.ts`: the process's copy on `globalThis`, Redis's list `api:keys:v1` at most once in 5 minutes, the table only when that list is missing) and written only in `src/services/api-keys/store.ts` (`scripts/smoke-api-keys.ts` fences the table); only a key's SHA-256 and its prefix are stored. A request makes no database query and no Redis command in the steady state (the rate limit is in memory, `src/lib/api-v1/rate.ts`), and no console line or Sentry field holds a key, its hash, an origin, a place name or coordinates (`lat`, `lon` and `city` are scrubbed from Sentry's URLs; `scripts/smoke-api-v1.ts` checks the run's logs).
- A summary voice note is the two-host show or the calm single voice by `User.voiceFormat`, read only through `voiceFormatOf` (`src/services/voice-show/types.ts`: anything but `'calm'` is the show) and made by the one pipeline (`produceShowVoice` → `writeShowScript` → `toShowLines` → `generateShowVoice`, each taking the format; the calm prompts in `src/prompts/voice-show/calm-*.ts` read the show modules' `kindRules`, `factRules`, `familyLines`, `addressRule` and `POINTING_RULE`, so a facts fix is made once). The show's prompts and TTS requests are pinned byte for byte by `scripts/fixtures/voice-show-golden.json` (`scripts/smoke-voice-calm.ts`; re-record with `--write-show-golden` only when the show itself is meant to change). The calm voice per language is `CALM_VOICES` (`src/services/voice-generator.ts`; the owner's picks by ear from the blind round) and its style `CALM_STYLE`, one string on every paragraph, frozen with that pick: changing either means a new listening round.
- A guest answer (Ask FamCal in a chat, Telegram Guest Mode, `src/services/ask-in-chat/`) shows only busy and free times, one line per person, never an event's name: the caller is the guest message's sender, matched by `telegramId` alone (the webhook gate's own lookup), and the times come from `readBusyDays` (`busy.ts`) through the summaries' reader (`readLookaheadEvents`) on the summary's calendars, split by person only by `peopleOf` (`people.ts`, on `getCalendarsWithOwners`: a calendar the partner owns is the partner's, the kids' when labelled kids, and the caller's when the partner labelled it spouse, i.e. about the caller, through `labelsFromViewerSide` like the summaries; a kid's calendars that share a name in either language are one line). The answer is in the language of the message replied to, as the model reads it in the same call (`language`: he, en, ru; otherwise, or with no message, the caller's), for every line after the model answers. The model gets no name: it says who was asked as a kind, or a name as the messages write it, which `askedLines` matches locally; no console line or Sentry field holds that name or a person's. The update's shape is read only in `update.ts`; a bare reply is answered only from the caller of the answer it replies to (`answersThis`). No console line or Sentry field holds either message's text, an event's title, a name, a chat id or the query id (the one-answer claim is the query id's hash), and `src/lib/sentry-scrub.ts` drops a `guest_message` body.
- No secret value reaches the server logs: `instrumentation.ts` installs `src/lib/console-scrub.ts`, which replaces the value of every environment variable whose name matches its `SECRET_NAME` (…_TOKEN, …_SECRET, …_API_KEY, …_PASSWORD, the database and Redis URLs) in each console line. Name a new secret to match, or its value is printed unscrubbed; `scripts/smoke-console-scrub.ts` pins the install.
- Every web sign-in (the WhatsApp link, Telegram, Google, an email code) and every web sign-up ends in `finishSignIn` (`src/lib/web-session.ts`): it refuses a suspended or banned account, sets `__Host-famcal_session` with the way, the sign-in time and the proved-at (`pa`, the one place a fresh one is set: page-data's renewal and Remove issue a session again only through `reissueSessionToken`, which carries it over, and Connect Telegram's hour reads it; `scripts/smoke-web-session.ts` #4c), and redirects. An account is made only by `createAccount` (`src/services/user-service.ts`), the one creation step of /start, a first WhatsApp message and the sign-up on famcal.bot (the ban check, the user and a web way in one transaction, the first FamCal calendar, one `[account] created` line); `scripts/smoke-account-create.ts` fails on any other `prisma.user.create`. `SignInIdentity` rows (the Google and email ways) are read and written only in `src/services/web-signin/identities.ts` (the Google way, the email way and the email code's account lookups) and the WhatsApp-into-Telegram merge (`src/services/account-linking.ts`), and nobody is matched by an address, a name or a phone number they typed: Telegram by the token's `id` claim (never `sub`), Google by its `sub`, an email by the code mailed to the address stored on the account (a sign-up code goes to the address typed, behind Turnstile, and only the right code proves it). The one address match is Google's own: the account a Google Calendar is connected from, by its keyed hash and a live check with Google (`matchCalendarAccount`, `src/services/web-signin/calendar-account.ts`). `findWayByAddress` reads an address just proved (Google's verified email, a right code) only to stop a second account, never to sign anyone in. Two accounts are joined only after Add Google or Add email proved, in a flow the person started, a way of the account to join, and only one with no chat that isn't the person's partner (`offerJoin`, `src/services/web-signin/join.ts`); the question and the merge read one rule set (`mergePlan`). A Google Calendar consent finishes in a browser only for the session of the account that started it (`POST /api/oauth/claim`; anyone else's press uses it up and connects nothing). A web session ends only through `User.sessionsValidAfter`, read in the user row every request already reads (sign out on all devices, removing a way, a suspension and a ban move it), never through a session table or a query of its own. Adding a way on the web (Add Google, Add email, Turn on, Join) and connecting a Google account from a browser (the consent start, a Copy to Google that asks Google's consent (the first one, or Approve in Google after Google stopped it), Finish here), and deleting one's own account in Settings (`POST /api/account/delete`, which also asks the same-origin check and `{ confirm: true }` and refuses an admin), need a sign-in from the last hour (the session's `pa`, never its sign-in time), asked through `refuseStaleSignIn` / `recentlyProved` (`src/lib/recent-sign-in.ts`) and never in the Mini App (initData is not asked); `scripts/smoke-recent-sign-in.ts` lists the guarded files. No console line or Sentry field holds an email address, a code, a token (Turnstile, connect, join, invite), a state or a name. `scripts/smoke-signin-setup.ts` holds the `SignInIdentity` file list.
- A browser notification (web push) goes only to an account with no chat, and only through `sendWebPush` (`src/services/web-push/send.ts`): it builds each request with the `web-push` library's `generateRequestDetails` (never its `sendNotification`), sends it through `fetchWithRetry`, never throws, and logs one `[push] user <id>: <kind> sent to N of M devices` line. A device (the browser's endpoint and keys) is read and written only in `src/services/web-push/devices.ts` (`scripts/smoke-push-devices.ts` fences `prisma.pushDevice`), only for a known push service's host (`PUSH_SERVICE_HOSTS`, because the server POSTs to every stored endpoint), and at most 10 an account. `canReachByPush` (`src/services/web-push/reach.ts`: push configured, no chat, a device) is the one reach rule, read by every Telegram gate of reminders and alerts; the push branch sits in the no-chat branch only, so a Telegram or WhatsApp account never gets one (the subscribe route refuses an account with a chat, and connecting a chat deletes its devices). `sendWebPush` does not ask the pause: each scheduled caller (the reminder pass, the event alerts, the briefings, the Google reconnect message, the trial-ended notice) asks `isPaused(user, at, '<its kind>')` first, while the partner notices and "Notifications are on" answer a person's action and do not; `pushTtlSeconds` (with `nextPauseStart`) makes a waiting push expire before the next pause window, at the event's start for an alert, and never later than 24 hours. No endpoint, key, notification title or body reaches a log, Sentry or the cache: `src/lib/sentry-scrub.ts` drops `endpoint`, `p256dh`, `auth` and the push services' URL paths, a push route reports a database error only through `captureSignInFailure` (a Prisma message can hold an endpoint), and the alert cache holds a has-device flag, never a device. The four writers that move `User.sessionsValidAfter` (sign out on all devices, `removeSignInMethod`, which keeps the device it was pressed on, `suspendUser` and `banIdentifier`) delete the account's devices in the same write with `deleteDevicesOf` and call `afterDevicesChanged` after the commit, so no device outlives its sessions and the sender checks no session. The VAPID key pair is made once and never changed (new keys cut every device off). `scripts/smoke-web-push-send.ts` pins the sender, `scripts/smoke-push-session-end.ts` the four writers and `scripts/smoke-push-reach.ts` the reach rule.
- Every Telegram Stars payment is credited only by `creditPayment` (`src/services/subscription-service.ts`): one transaction that inserts the payment's `Payment` row (its charge id is unique, so a second delivery of the same `successful_payment` credits nothing, even after a refund), then sets the plan paid for and the month. A refund names its `Payment` row (`refundPayment`, `src/services/admin-refund.ts`), and ends the plan only when that payment funds the current month. Everything shown before or after a payment (the plan screen's terms, the invoice, the confirmation, `/terms`, the policy links after a first contact) comes from `src/lib/plan-disclosure.ts`, and the seller's details only from `SELLER` (`src/lib/seller.ts`): the ID number is shown in the bot only, never on the website (the owner's choice), and a detail not given yet is `null`.
- The Privacy Policy and the Terms (`legal.*` in `messages/`) are approved by the owner, and the Hebrew and Russian texts bind their readers as the English does. Change their meaning only on the owner's word, in all three languages at once, with a new `LEGAL_UPDATED` (`src/site/legal.ts`). Their plan numbers are written by hand, never interpolated: `scripts/smoke-terms-plans.ts` fails when the Terms or the bot's copy disagree with `src/config/plans.ts` (the limits and the trial) or with `REFUND_WINDOW_DAYS` (`src/lib/refund-eligibility.ts`).
