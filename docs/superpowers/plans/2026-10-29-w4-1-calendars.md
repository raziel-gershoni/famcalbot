# W4-1: the Calendars screen in the app's design — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** the Calendars screen (`/[locale]/calendars`) moves onto the app kit: light and dark, all three languages in messages, an in-app delete confirmation, a back button in a browser, a row that leads to the Google calendars, and errors in words.

**Architecture:** `CalendarsClient` becomes an `AppScreen` on the grouped ground (like Settings, Partner and Subscription) built only from `components/app-ui`. Editing a calendar moves from an inline card into a bottom sheet. The Copy to Google rows keep their logic (`google-copy-client.ts` untouched) and get the kit's markup. PageGate draws the page in the 'app' look, and the 'light' look, which only this page used, is deleted.

**Tech Stack:** Next.js 16 client components, next-intl `useTranslations`, the kit in `components/app-ui` (`AppScreen`, `ScreenHeader`, `SectionLabel`, `FormCard`, `FormRow`, `ListRow`, `SwitchRow`, `RadioCard`, `TextField`, `SaveBar`, `Notice`, `BottomSheet`, `Tag`, `FORM_CSS`), lucide icons, smoke scripts run with `npx tsx`.

**Spec:** `docs/superpowers/specs/2026-10-19-screens-and-colours-design.md` (§4 the kit, §5 the recipe) and the owner's W4 decisions of 2026-10-28: Calendars first; two screens cross-linked (not merged); no mockups, built on the kit; Select calendars keeps its instant save (that is W4-2, not this plan). The Copy to Google behaviour is `docs/superpowers/specs/2026-10-20-google-sync-design.md` §1 and §5 (unchanged here). ## Global Constraints

- Only kit pieces and `--ch-*` tokens; no Tailwind colour classes, no hex colours in CSS, no `:hover`-only styling, logical properties only (`margin-inline-start`, not `margin-left`), every tap target at least 44 px. Any CSS added passes `lintCss` (`scripts/lib/css-lint.ts`).
- Light and dark both come from the kit (`AppScreen` sets `data-theme` from Telegram or `prefers-color-scheme`). Nothing on this screen may assume a light background.
- lucide icons only, `aria-hidden`; no emoji.
- No inline user-facing strings: the inline `COPY` object goes. Every string is in `messages/{en,he,ru}.json` (`calendarsPage.*`, plus existing keys reused: `ui.*`, `calendars.categories.*`, `googleCopy.*`), with the exact texts given below. The i18n parity check, `smoke-he-neutral.ts` and `smoke-ru-formal.ts` must pass (they now see this screen's copy).
- Hebrew addresses the person gender-neutrally (plural forms, infinitive or noun buttons, no slash forms). Russian is formal.
- Behaviour that stays exactly as it is: the requests and their bodies (`POST /api/native-calendars` `{name, initData}`, `PATCH /api/native-calendars/<id>` `{name, color, labels, privacy, initData}`, `DELETE` with `deleteCalendarBody(googleCopy, initData)`); `getInitData()` returning `readInitData()` (smoke-initdata-header #9 pins it); the drawn colours (`displayColours` with the Google colours); every Copy to Google state, the polling (`COPY_POLL_MS`), the refresh on `visibilitychange`, the consent wait and its expiry, and the Remove/Keep question's wording (`googleCopy.unlink.*`). A partner's calendar stays read-only.
- One request at a time on the page (the Partner screen's `run` pattern): the running action shows a spinner, the others are disabled. Every failure is logged (`console.error('[calendars] …')`) and said in the page's language.
- Back has one owner: `AppScreen onBack` (Telegram's BackButton, and the header's own back in a browser). It closes an open sheet first (a confirm step goes back to the edit step), never while a request runs, else goes to `/${locale}/dashboard?user_id=…`. The direct `useTelegramBackButton` call in this file goes away.

## Review Focus

1. A Hebrew (RTL) person in dark mode: every row, the sheet, the swatches and the chevrons mirror, nothing is white-on-white or unreadable, and no English text shows (names of colours included).
2. Saving an edit that the server refuses (404 deleted elsewhere, 429 too many changes, 401 an expired Telegram session, 500): the sheet stays open with the entered values and says what happened; nothing on the list changes.
3. Deleting a calendar whose Google copy is on: the Remove/Keep question shows in the sheet, the chosen answer reaches the DELETE body, and Cancel leaves everything as it was; deleting the only calendar is not offered.
4. A WhatsApp person opening the page in a browser (no Telegram): the header's back works, the Google row's link works, and nothing calls a Telegram-only API unguarded.
5. A person whose partner shares calendars but whose copies are not shown, and a person with no partner: the partner section appears only when there are shared calendars, and its heading reads naturally with and without the partner's name.

**What the screen shows, top to bottom** (`AppScreen ground="grouped" onBack={back}`, `<style>{FORM_CSS}</style>`, then `ScreenHeader title={t('title')} backLabel={ui('back')} onBack={back}`, then `.ch-form-page`):

2. **Your calendars:** `SectionLabel` `yours`, then a `FormCard`:
   - one `ListRow` per own calendar: title = a 12 px `.ch-swatch-dot` in the drawn colour, then the name in `<bdi dir="auto">`; meta = the privacy line (`privacyPrivate` / `privacyViewer` / `privacyEditor`); tags = a `Tag tone="muted"` per category other than "yours" (`calendars.categories.*`), with the primary one as `Tag tone="accent"`. 4. **The partner's calendars** (only when there are shared calendars): `SectionLabel` `sharedBy` with `partnerName`, or `sharedByPartner` without one; a `FormCard` of non-interactive rows: the dot and the name, the hint `calendarsPage.sharedAccess.view|edit`; under the card, when copies are shown and the view has `ownerName`, `NonOwnerCopyLine`.
5. **Google Calendar:** `SectionLabel` `google`, a `FormCard` with one row by `google.state`, and `googleHint` under it as `.ch-form-fixed`:

   - 'reconnect': label `googleReconnect`, same as 'none'.

**The edit sheet** (`BottomSheet label={c.name} closeLabel={ui('cancel')} closeDisabled={busy}`), for an own calendar:
- `TextField` `name` (maxLength 60, the value the person typed stays after a failed save);
- `SectionLabel` `color`, `ColorSwatches` over `CALENDAR_PALETTE` with `calendarsPage.colors.<name>` labels; the saved colour is chosen (the swatches show the saved colour, not the drawn one, as today);
- `SectionLabel` `categories`, a `FormCard` of five `SwitchRow`s in this order: primary, yours, spouse, kids, birthdays (label `calendars.categories.<id>`, hint `categoryHint.<id>`); toggling builds the same `labels` array as today (no exclusivity on the client: the server keeps one primary);
- `SectionLabel` `privacy`, a `RadioCard` with the three privacy options;
- a `SaveBar` (`ui('save')`, busy, the error);
- a `FormCard` with a danger row `delete` (`ch-form-row ch-danger-row`), or, when this is the only own calendar, a disabled row with the hint `onlyOne`.
- **Delete** turns the sheet into its confirm step (same sheet, `back` returns to the edit step):
  - copy off (or no copy): `deleteTitle` (with the name in `<bdi>`), `deleteBody`, one danger button `delete`;
  - copy on: the question `googleCopy.unlink.question` and two buttons, `googleCopy.unlink.remove` (danger) and `googleCopy.unlink.keep` (primary), each deleting with that choice. Before asking, the copy rows are loaded when not loaded yet (today's `remove()` rule: a delete never goes without `googleCopy` unless a loaded view says the copy is off; a failed load is `errors.delete`).
  - A failure keeps the sheet on the confirm step with the error.

**The create sheet:** `TextField` `name` with `namePlaceholder`, a `SaveBar` labelled `create`; `calendar_limit_reached` shows `Notice tone="error"` `errors.limit` with the action `seePlans` → `/${locale}/subscription?user_id=…`.

**The Remove/Keep question for turning a copy off** (the switch of an "on" row): the same `BottomSheet` pattern with `googleCopy.unlink.question`, Remove (danger), Keep (primary); Cancel is the sheet's close.

**GoogleCopyRow in the kit:** a `ch-form-row` with the switch (`role="switch"`, `aria-checked`, `aria-label={googleCopy.switchLabel}`, `ch-switch` / `is-on`), the label = the calendar's name, the hint = the busy line (with `.ch-form-spinner`), the waiting line, or the status line (a status that needs the person in `--ch-danger`, as today's rose); the unsupported-count line as a second hint; under it, when there is one, an action row (a `ch-form-row` button in the accent colour: `actions.openGoogle` while waiting, else the row's action label); an error as `FieldError`. Same states and labels as today.

**Errors for a save (PATCH):** by status and code: 404 or `not_found` → `errors.notFound` (and the list reloads); 429 → `errors.tooMany`; 401 or 403 → `errors.reopen`; anything else → `errors.save`. Create: `calendar_limit_reached` → `errors.limit`, 429 → `errors.tooMany`, 401/403 → `errors.reopen`, else `errors.create`. Delete: `cannot_delete_last` → `onlyOne`, 404 → `errors.notFound`, 429, 401/403 as above, else `errors.delete`. A thrown request (network) is the generic one of its action. Never the server's raw text.
