# Telegram library 2.x Implementation Plan

> **For agentic workers:** one implementer per task, in order, on one branch; one final whole-branch review. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Move from node-telegram-bot-api 0.66 (class `TelegramBot`, the deprecated `request` stack) to node-telegram-bot-api 2.4.0's `Api` client, with no change anyone sees: the same messages, buttons, voice notes, photos, payments, guest answers and error handling.

**Architecture:** One `Api` built in `src/services/telegram/bot.ts` with `{ maxRetries: 0, timeoutMs: 0 }`, so the library never retries a send by itself and has no timeout of its own. `getBot()` keeps its name and returns the `Api`. Every call takes one params object. Every failure is read through one helper, `telegramErrorInfo` (`src/lib/telegram-errors.ts`), because 2.x errors have no `.response`. The test fakes come from one helper, `scripts/lib/fake-telegram.ts`.

**Tech Stack:** node-telegram-bot-api 2.4.0 (zero dependencies, built-in fetch, ESM + CJS builds, types included), TypeScript 5.9, tsx smokes (`scripts/smoke-*.ts`, run by `scripts/ci-smokes.sh` with fake env only).

**Spec:** the owner-approved dependency evaluation (decision 5, 2026-11-10: "Telegram 2.x as its own task after B, not urgent"), scratchpad `deps/evaluation.md` section 2 and `deps/report-telegram.md`; the code survey with every call site and error reader is `tg2/survey.md` in the same scratchpad (section numbers below refer to it). Reference copy of the 2.4.0 package: scratchpad `ntba2/package` (`dist/core/*.d.ts`, `dist/node`, `dist/types`).

## Global Constraints

- Never run `npm run build` (it migrates the production database); use `npx tsc --noEmit`, `npm run lint`, `bash scripts/ci-smokes.sh` and `npx next build`. Run every npm and node command on Node 22: `npx -y node@22 $(command -v npm) …`. Never `npm audit fix`.
- Never read or print any `.env*` value; grep with `--exclude='.env*'`. Smokes run with fake env only (for a single smoke: `env $(sed -nE "s/^  '([A-Z_]+=[^']*)'$/\1/p" scripts/ci-smokes.sh) TZ=Asia/Jerusalem npx tsx scripts/smoke-x.ts`). Never run `scripts/setup-webhook.ts`, and nothing calls the real Telegram API.
- `"node-telegram-bot-api": "2.4.0"` exact (the 2.x line ships every week or two; a bump is a deliberate change). Remove `@types/node-telegram-bot-api` (2.x ships its own types).
- The `Api` options are `{ maxRetries: 0, timeoutMs: 0 }`, nothing else. The library's default retries every method twice, sends included, and times out at 5 minutes; both break the repo's rules (one retry loop, `src/utils/fetch-retry.ts`, only around the guest answer; no timeout of our own; `src/cron/handlers.ts:356` relies on "no request timeout").
- Never swap `user.id` and `telegramId`: every `chat_id` and `user_id` keeps the value it has today.
- Read a library error only through `telegramErrorInfo`. Match on the error's `code` and fields, never `instanceof`: the package ships an ESM and a CJS build, and an `instanceof` across the two is false.
- No console line or Sentry field holds the bot token, a message text, a name, a chat id or a guest query id (CLAUDE.md, the console-scrub and guest-answer rules).
- No behaviour change: same wire fields, same file names, same retries, same stored "unreachable" reason text, same log lines except where a step names a change.
- Commit per task in the repo's style (`refactor(telegram): …` / `chore(deps): …`), ending with the session trailer lines.

## Owner decisions this plan assumes

1. Pin 2.4.0 exactly.
2. Drop the local polling bot: `npm run dev` becomes `next dev`. Today `scripts/dev.ts` also starts a polling bot that answers only /start and /connect, and only with a dev bot token whose webhook is off. 2.x has no `onText`/`stopPolling`, so the alternative is porting it to 2.x's `Bot` (about one more hour). Prod is the only place the bot is tested.

## Review Focus

1. A send whose answer is lost (a dropped connection, a gateway's HTML 502) must reach Telegram once, never twice: the `Api` makes exactly one request (Task 1, wire smoke).
2. A reminder ping refused with 400 or 403 must not be retried every pass, and a blocked user must still be marked unreachable with the same stored reason ("Forbidden: bot was blocked by the user", without 2.x's "403: " prefix) (Task 2, error smoke).
3. A 2.x network error whose cause carries the request URL must not put the bot token in a console line or in Sentry (Task 2 console-scrub case; Task 3 rewrite of smoke-bug-batch-safety's EFATAL check).
4. Voice notes and the weather photo must arrive as files with today's file names and types: voice as `voice-….opus` with `application/octet-stream`, the photo as `weather.png` with `image/png` (Task 1, wire smoke).
5. A keyboard in an edit must be sent once as JSON, never double-encoded, and link previews must stay off where they are off today (Task 1, wire smoke).

```ts
/**
 * What a failed Bot API call says, read from node-telegram-bot-api 2.x's errors by their `code` and fields (never
 * `instanceof`: the package ships an ESM and a CJS build, and a class from one is not the other's).
 * - refused: Telegram answered `{ ok: false }` (its status and words; a 429's wait in ms).
 * - no-answer: fetch threw, or a 5xx came back that is not Telegram's JSON (a gateway's page).
 * - unreadable: an answer under 500 that is not JSON (a proxy's page); its status is lost.
 * Anything else (our own bug, another library's error) is null.
 */
export type TelegramErrorInfo =
  | { kind: 'refused'; status: number; description: string; retryAfterMs: number | null }
  | { kind: 'no-answer'; code: string }
  | { kind: 'unreadable'; code: string };

export function telegramErrorInfo(error: unknown): TelegramErrorInfo | null {
  if (!(error instanceof Error)) return null;
  const e = error as Error & { code?: unknown; errorCode?: unknown; description?: unknown; parameters?: { retry_after?: unknown } };
  if (e.code === 'ETELEGRAM' && typeof e.errorCode === 'number') {
    const after = e.parameters?.retry_after;
    return {
      kind: 'refused',
      status: e.errorCode,
      description: typeof e.description === 'string' ? e.description : e.message,
      retryAfterMs: typeof after === 'number' ? after * 1000 : null,
    };
  }
  if (e.code === 'EFETCH' || e.code === 'ETIMEOUT') return { kind: 'no-answer', code: e.code };
  if (e.code === 'EPARSE') return { kind: 'unreadable', code: e.code };
  return null;
}
```
