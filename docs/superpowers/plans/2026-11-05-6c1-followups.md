# 6c-1 follow-ups Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The four follow-ups the owner approved on 2026-11-05 after the 6c-1 final review ("go with recommended"): adding a way to sign in on the web needs a sign-in from the last hour; a ban also records the Google way's email address; two Privacy Policy wording fixes.

**Architecture:** One server-only helper (`src/lib/recent-sign-in.ts`) owns the hour rule that Connect Telegram already has; every route that adds a sign-in way or connects a Google account from a browser cookie asks it before any redirect, email or write, and again where the add finishes. The Mini App (Telegram initData) is never asked. The ban reads the Google way's stored address through the existing `accountWays` and records it in the existing `BlockedIdentifier.email` column (no migration). The legal texts change in all three languages with a new `LEGAL_UPDATED.privacy`.

**Tech Stack:** Next.js 16 route handlers, Prisma, Upstash Redis, next-intl (`messages/{en,he,ru}.json`), smoke scripts under `scripts/` (run through `scripts/ci-smokes.sh` with the fake env).

**Spec:** `docs/superpowers/specs/2026-11-03-web-sign-up-design.md` (the 6c-1 spec; Task 1 appends its §10 "Follow-ups (owner 2026-11-05)"). The code map with file:line for every step is `.superpowers/sdd/2026-11-05-6c1-followups/map.md` (read the section for your task).

## Global Constraints

- The hour: `RECENT_SIGN_IN_MS = 60 * 60 * 1000`, compared against the session's `provedAt` (the cookie's `pa`) only, never `signedInAt`; `now - provedAt < RECENT_SIGN_IN_MS` passes (59:59.999 passes, 60:00.000 is refused).
- A request authenticated by Telegram initData (`verifyUserAuth(...).via === 'telegram'`) is never refused by the hour.
- Refusal answer: HTTP 403 with JSON `{ ok: false, error: 'stale-sign-in' }`; refusal log: `[recent-sign-in] user <id>: <tag> refused: the <method> sign-in is not recent` (user id and method only, nothing else).
- Remove a sign-in way stays ungated (a stale session can always remove a way).
- No console line or Sentry field holds an email address, a code, a token, a state or a name (CLAUDE.md "Every web sign-in" rule).
- Every user-facing string in `messages/{en,he,ru}.json`; Hebrew gender-neutral (infinitive or impersonal), Russian formal ("вы"), natural, never word for word.
- `LEGAL_UPDATED = { privacy: '2026-11-05', terms: '2026-11-04' }` (the Terms text does not change).
- Never run `npm run build`; gates are `npx tsc --noEmit -p .`, `npm run lint`, `bash scripts/ci-smokes.sh`.

## Rulings (controller, 2026-11-05)

- R1: a WhatsApp-link session (`method === 'wa'`) counts like any session for these gates (refused after an hour), and the screens show the WhatsApp hint (`pageGate.browserBody`) instead of a Sign in again button. Connect Telegram keeps refusing `'wa'` always (unchanged). Cost if wrong: a WhatsApp-only person with a link older than an hour asks for a new link before adding Google.
- R2: Turn on (`POST /api/signin-methods/calendar-on`) and Join (`POST /api/signin-methods/join`) are gated too: both add ways to the account. Cost if wrong: one extra sign-in on those two.
- R3: the screens learn of a stale sign-in on the press (like Connect Telegram today), not in advance: no new field on `GET /api/signin-methods`. Cost if wrong: one wasted press.
- R4: the Privacy Policy's "Signing in." paragraph ("If you sign in with Google, FamCal asks Google only for…") is not changed: the owner approved only the processors line. Raised in the report.
- R5: no backfill of existing bans (report only): Google ways exist only through the web sign-in, which stays hidden until its Railway variables are set.

## Review Focus

1. A stale cookie together with valid Telegram initData: the request passes (initData wins in `verifyUserAuth`).
2. Add Google started on a fresh cookie whose hour runs out on Google's consent screen: the callback refuses (`finishAddGoogle` checks the flow's `provedAt`), writes no `SignInIdentity` row, sends no notice, sets no cookie.
3. An email code requested in the hour and confirmed after it: confirm refuses and leaves the code and the pending key unconsumed.
4. A ban of an account whose Google address equals its email way's address writes one email row, not two; a stored Google address `normalizeEmail` can't keep (null) is skipped and the ban still succeeds.
5. A link entry or a flow written before the deploy (no `provedAt` field) is treated as a Mini App start (unchecked): it expires within minutes.
